# Implementation checkpoints

## Architecture

`FFXILauncher.Core` owns account metadata, login evidence/state transitions, viewport mapping, and platform interfaces. `FFXILauncher.Desktop` owns the Avalonia dashboard and Windows process/credential adapters. The login engine must keep a single foreground input lease across all accounts. Credential reads occur only after verifying the target process, window, and password field.

The account's configured character is a target, not an observed identity. Process ownership requires PID plus creation time. Before any destructive operation, verify both again. A missing heartbeat alone must never authorize termination.

## Windows login validation and remaining coverage

1. Validate actual Windows reference screens, region, POL member layout, separate POL/SE credential requirements, and OTP behavior.
2. Implement Windows client-area capture and checkpoint classification with visual anchors. Geometry scaling is permitted only for validated layouts; fixed-size and anchored panels need distinct transforms.
3. Validate keyboard/scan-code entry and mouse fallback, foreground checks, integrity-level compatibility, modifier handling, and focus loss. Unknown screens pause without input. Avoid shell commands, clipboard secrets, and general-purpose command injection.
4. Add fine-grained checkpoints based on the Deck script: member selection, login dialog/editor, masked password, connect, POL home/play/confirmation, title acceptance, character selection/confirmation, world entry.
5. Verify the exact character confirmation, then the world through an advancing fresh addon heartbeat associated with the owned process.
6. Test wrong member/character, unexpected dialog, focus theft, resizing, DPI/monitor changes, slow network, authentication failure, and OTP.

## Then: maintained multi-account sessions

- Expand the implemented startup process discovery and provisional character imports into fully verified restart reconciliation; resolve identical names on different worlds.
- Complete the login adapter behind the existing account policy controls and cancellation. Official maintenance windows and recovery holds are implemented. Scheduled shutdown preserves the maintaining policy; manual shutdown suppresses it. Automatic scheduled shutdown is gated on login readiness.
- The independent FFXIManager addon implements authenticated session-bound graceful-shutdown IPC and character/world heartbeats. Expand telemetry with PID binding, zoning/loading and connection state. HaupBridge currently has no shutdown operation; existing instances were not modified.
- Recovery ladder: recognized dialog → return to login checkpoint → bounded retry → terminate only verified owned process → fresh launch. Persist retry budgets and respect intentional shutdown.
- Correlate widespread failures and suspend mass retries during network outages. Authentication errors require attention; never loop passwords.
- Tray lifecycle with explicit exit semantics and a global automation pause.

## Identity and maintenance

The proven SteamDeck configured-POL flow establishes SE ID plus SE password as the minimum consistent user inputs when POL already saves its password. Keep character/world and POL member/profile mapping as reusable/discovered context, with explicit overrides only for missing or ambiguous mappings. Imported cards display SE IDs or an explicit setup-needed message. The current Windows preview accepts this minimum setup and implements login automation; automatic discovery of saved POL member identities remains pending. Local member password is a distinct conditional secret, and OTP accounts require attended fresh codes.

Character identity is name plus world. Use a fresh addon report for the current world or user-confirmed setup. External data may suggest a world only when the latest available lookup has exactly one matching world; retain its source and timestamp, and handle transfers/multiple matches as uncertain. A public player page is not proof of ownership or current online status. The FFXIAH link is implemented; a documented lookup provider has not been verified.

Use the official `/ff11us/info/list_mnt.shtml` and linked news notices. Parse explicit date ranges and PDT/PST/UTC offsets; store UTC and display local time. Track all-world and matching world notices, including multiple worlds mentioned in a title. Hold recovery throughout overlapping windows and the two-minute end grace. Poll every five minutes and require a check no older than fifteen minutes. Unparsed relevant notices require review. The five-minute early shutdown policy is optional and requires maintaining plus a ready relogin adapter. Revised notices replace cached times.

POL profile nickname, character name, POL ID, and SE ID are separate fields. A shared SE ID does not identify a unique POL service account. Local `login_w.bin` was located read-only; no reliable nickname/SE-ID parser has been established. Never alter this database to guess a mapping.

Installation paths now auto-detect from running processes and Windower module locations, then known folders/registry as fallback. Preserve manual overrides; resolve multiple installations explicitly. Reuse Default or a sole Windower profile when no override exists. Bulk selection is independent of account automation policies; persist a group shutdown policy before IPC dispatch, and never re-enable accounts outside the chosen launch group.

### Addon deployment and maintenance evidence (0.2.3)

The Windows installer copies the bundled payload, excludes its data directory, and retains the existing private control token. It prepends the load command before startup waits while preserving original bytes/BOM/newline conventions, backs up modified existing init files, and refuses to overwrite concurrent edits. Existing load entries are left alone. Running games need one manual load/reload; bootstrap injection is not required.

Original non-injected incoming 0x017 packets are parsed with Windower's packets library. Only modes 6/7 (system messages) containing English maintenance wording produce a bounded seven-line `.alert` record. Completion/cancellation notices do not create holds. Records retain session, character/world, registration and observation timestamps, fixed source marker and sanitized text. Logout removes the heartbeat but retains maintenance evidence. The manager validates records and filename identity, displays world-scoped warnings, and applies holds to manual auto-login requests and watchdog recovery. A fresh relevant official schedule releases holds after its end plus two minutes; unknown timing remains held until the user clears alerts for selected worlds. Alerts do not infer a global scope or classify arbitrary crash/error causes. Live notice samples, additional languages/packet types and POL errors remain pending validation.

Packet references: https://github.com/Windower/Lua/blob/dev/addons/libs/packets/fields.lua and https://github.com/Windower/Resources/blob/master/resources_data/chat.lua.


### Protected Windows installations (0.2.4)

Normal deployment first attempts the existing installer. An access-denied error starts the packaged desktop executable with the `runas` shell verb in a helper-only mode before the single-instance mutex or Avalonia UI. It deploys only the bundled addon and startup entry, then exits. The caller handles canceled UAC prompts, waits asynchronously, and verifies startup and a temporary write in the IPC directory as the original user. Helper arguments are separate process arguments, not shell commands. The helper rejects a different Windows user SID before filesystem writes, preserving the original user's token/data ACL. No permissions are granted to Everyone and no Windower-wide ACLs are loosened. Standard users needing a different administrator account remain unsupported by this helper; the app reports that case explicitly.

Isolated native checks cover normal deployment without elevation and rejection of malformed/wrong-user helper invocations. The UAC consent interaction in the real protected installation still needs user validation.


### Late-loaded addon attachment (0.2.5)

The manager now checks for unique configured character processes with fresh matching addon heartbeats every three seconds, and before individual, selected or all-managed shutdown. All-managed targets are gathered after attachment, so loading the addon after starting the app no longer leaves the action with an empty target set. Missing, stale, mismatched-world or ambiguous evidence remains ineligible. Native regression validation uses isolated synthetic telemetry with read-only process inspection; it never dispatches shutdown to the live game.


### Complete shutdown and hung-process cleanup (0.2.6)

Shutdown captures the original managed process and tracks it through character logout, window title changes and actual OS exit. The UI shows IPC dispatch, character disconnection and elapsed shutdown time. An acknowledged dispatch that has waited 90 seconds without a fresh heartbeat can force terminate only that original process. The termination helper pins the process handle, validates PID creation time and executable path, terminates that handle without broad process-name/tree kills, and waits up to 15 seconds for verified exit. Active game heartbeats and missing dispatch acknowledgment block automatic cleanup. The per-account Force close action explicitly stops maintaining and terminates the same verified process. Cleanup errors leave startup blocked by the existing process. Pending shutdown progress is currently held in the running manager; keep it open until exit verification completes.

Native tests terminate disposable PowerShell sleepers only, reject mismatched timestamps/images and verify a second unrelated sleeper survives.
