# Windows startup troubleshooting

The installed manager exposes the same bounded test interface used during development. A successful process launch alone does not prove that POL rendered a login screen or that a character entered the world.

## Windows access from WSL

On the original development machine, PowerShell is available at `/mnt/c/Windows/System32/WindowsPowerShell/v1.0/powershell.exe`. Invoke repository scripts through their Windows UNC paths, for example `\\wsl.localhost\FedoraLinux-42\home\mzipkin\git\FFXI-Launcher\tools\windows-crash-report.ps1`. Restricted shells may require approved execution outside their sandbox for WSL interoperability. Windows administrator consent remains separate and is required for protected installation changes.

## Reproduce one account

1. Inspect running POL processes, the installed manager and its unattended scheduled task before starting anything. Preserve unrelated sessions.
2. Run `tools/windows-crash-report.ps1` during one launch. Its JSON includes Windows Application Error, Error Reporting and hang events, process/window samples, executable versions and local graphics-wrapper hashes. No matching event does not establish that the process is healthy.
3. The development script `artifacts/windows-login-control.ps1 -Operation launch -Character <configured-character>` requests a launch through the running elevated manager's authenticated `login-control` channel. This script is an ignored local artifact, not a shipped repository tool. It requires exactly one matching configured account and records the process identity returned by the manager.
4. `-Operation inspect` uses that exact tracked process and the existing window/readiness guards. `-Operation login` follows the saved login path and credential safeguards. Do not repeatedly submit credentials after an error. Successful full login requires the configured character/world and an advancing addon heartbeat.
5. If the disposable test process hangs, the same control's `-Operation close` targets only its tracked PID and creation time. Do not terminate all POL processes or replace shared installation files while a POL process is running.

The control capability token must remain private. Never include it, account credentials, or raw request files in reports. Do not overwrite account mappings, erase login caches or reinstall the manager as a first diagnostic step.

## Launcher crash when the official notice site is unavailable

On October 21, 2026, Windows .NET Runtime event 1026 recorded four launcher 1.0.22 failures (12:42:59, 17:22:17, 17:22:33 and 17:23:20 EDT) with `InvalidDataException: The official notice list format was not recognized.` The stack runs from `MaintenanceMonitor.RefreshAsync` through `MainWindow.CheckRecovery` into the asynchronous UI timer callback.

The official notice-list URL redirected to `/error/maintenance.html`, which returned HTTP 200 with Square Enix's service-unavailable placeholder. The monitor correctly rejected a response without notice links, but its catch filter covered `IOException` and omitted `InvalidDataException`, which does not inherit from `IOException`. The resulting unhandled exception closed the manager.

Version 1.0.23 handles unavailable/malformed notice responses, retains the previous snapshot and check time, reports that official notices are unavailable, and preserves the five-minute retry interval. Stale data still cannot authorize automatic recovery. Regression coverage uses a synthetic HTTP-200 maintenance page, a network failure, unchanged cache/freshness checks and successful recovery on a later valid response. The diagnostic collector also includes event 1026 and preserves unnamed event-data text containing managed exception stacks.

The repaired Windows package passed its payload verification, the maintenance regression and the full Windows dashboard/credential smoke suite. Core contracts and Linux dashboard smoke checks also passed. After installation through the normal unattended setup, version 1.0.23 was responsive with no new launcher crash events in the initial observation; all three existing POL processes retained their recorded creation times and responded. The user also confirmed that the launcher worked again. This validates the observed feed failure path, rather than every possible launcher crash.

### Requested login and idle controls

Version 1.0.24 distinguishes an explicit Launch profile/Start auto logins request from unattended recovery. An unavailable feed or unreadable notice no longer prevents a requested login. Known applicable maintenance windows, the configured shutdown lead time, session identity checks and credential/input safeguards still apply. Unattended recovery still requires a current, readable maintenance check; existing in-game warning holds are retained.

An idle account displays `No process tracked`. Graceful shutdown and Force close are disabled without a detected running process and refreshed on subsequent process observations. Force close remains available for a tracked startup process without a usable window; graceful shutdown requires a window. A maintenance-related refused launch is explained in Activity rather than replacing the idle process status with internal parser terminology.

Version 1.0.25 adds a shared three-attempt focus-recovery budget for initial focus and screen capture. Every focus operation revalidates the original PID, creation time and configured executable. Recovery rereads the screen and resumes the same engine state; it does not restart the login, retype a password or replay a failed input action. Loss of focus during an input action still stops that attempt. Cancellation, process replacement and a depleted recovery budget stop recovery. The earlier 1.0.24 UI trial confirmed that Launch profile opened POL, while its login stopped at the existing foreground guard; learned caches remained present.

## Running-process disconnect recovery (1.0.26)

Windows responsiveness and the original addon heartbeat can both remain healthy while POL displays a disconnected-session dialog. The addon reports a separate `.connection` file bound to its character/world/session nonce, registration time, report time and last genuine incoming packet. Injected packets do not refresh server liveness. Version 1.0.26 also excluded blocked packets and allowed inspection after one unsuccessful liveness read; the quiet-session correction below replaces that behavior.

For Maintain connection accounts, two matching numeric error reads identify POL-0250 or FFXI-4001/4002. Before acknowledging the first dialog, recovery also verifies the corresponding disconnect wording and revalidates the account/process. It clicks the recognized OK button or uses the confirmed dialog's default OK action, then waits for recognized game menus. Character-selection recovery uses the existing guarded route and enters no POL credentials in the old session. A further numeric error must match on two reads before fresh restart is requested. Credential rejection pauses recovery instead of retrying credentials.

Fresh restart pins and verifies the exact PID, creation time and POL executable, confirms exit, waits a short retry interval and runs the existing login route. A previously validated, unchanged account mapping may complete full validation on this new build specifically after confirmed disconnect cleanup. Older-build proofs still do not authorize ordinary unattended startup. Failed logins retain the existing retry delay; user cancellation, disabling Maintain connection, intentional shutdown, account remapping and active maintenance prevent recovery actions.

A truly nonresponding process requires 90 continuous seconds without either a rendering heartbeat or recent server activity before timeout cleanup. A stale heartbeat, generic error wording, unreadable screen or one unresponsive sample alone never authorizes termination. Support-center-only maintenance notices are excluded from game scheduling. Existing running addon instances need a reload to produce packet telemetry; fresh game processes load the updated addon automatically.

The October 23 live test confirmed Minibubble's FFXI-4001 and Hauplibond's FFXI-4002 dialogs on two reads, acknowledged each, confirmed the subsequent POL-0250, terminated only the respective tracked process, and automatically completed fresh login with character/world validation. Both replacement sessions produced current incoming-server timestamps. Windows OCR read `FFXI` as `FFXl` at the tested resolution; code recognition now normalizes only that prefix glyph while preserving exact numeric digits, dialog bounds and wording checks. Regression checks reject ambiguous digits.

Acknowledging an initial POL-0250 can also cause the old process to exit itself. Confirmed-disconnect recovery queues a fresh login in that case without attempting to terminate an already-exited process. The direct character-selection recovery route and the 90-second hang timeout were not separately exercised against live accounts in this trial; their decision and guard contracts were checked without disrupting healthy games.

At 07:00:15 UTC, Nanakia, Minibubble, Luckystrikes and Hauplibond all had distinct responsive replacement processes and matching fresh-session incoming traffic one second old. Nanakia and Luckystrikes were restored through explicit authenticated launch/full-login requests after the test update; their restoration is not counted as an end-to-end automatic disconnect-recovery pass. The final installed 1.0.26 DLL hash matched the tested package, its package check passed, and the three already-restored processes survived the final manager update unchanged. Core contracts (353 checks), Lua addon contracts, Linux dashboard smoke and the full native Windows smoke suite passed.

### Quiet-session focus correction (1.0.27)

A read-only October 23 observation correlated Hauplibond's unsolicited focus with inspection-only worker requests at 6:14 and 6:15 PM EDT. Its rendering heartbeat remained current, the packet timestamp advanced at intervals up to 61 seconds, and the inspections found no disconnect code. The 30-second server-traffic cutoff caused unnecessary OCR on this healthy session. A separate brief telemetry-read miss was also observed during the addon's remove/rename publication; the old boolean liveness check could treat such a miss as permission to inspect immediately.

Version 1.0.27 publishes and reads connection reports every 30 seconds, separate from minute stats and the existing login/shutdown rendering heartbeat. The first two consecutive missed or unhealthy checks cannot trigger OCR; the third permits a fresh report recheck before focusing the window. Any healthy, advancing report resets the miss counter, and replacing the tracked process starts a new observation period. A cached, unchanged report cannot repeatedly count as a new heartbeat. Reports have a 45-second freshness allowance for the 30-second publication cadence, and their packet age at publication can be up to 90 seconds to tolerate quiet sessions. A negative inspection defers repeat checks for five minutes while the same condition persists; resumed server traffic resets the delay. Activity records the reason for an inspection and whether it found a disconnect. No extra server requests or packets are generated.

Addon 0.3.8 counts original incoming packets as network receipt even when another addon blocks their game processing. Injected packets remain excluded, and blocked packet contents still cannot update stats or maintenance alerts. The connection report retains its original six identity/timestamp lines and adds last-unblocked/last-blocked timestamps and their counters, without packet contents. Both the legacy six-line and current ten-line reports are accepted. Windower exposes these as separate flags in its [incoming-chunk event](https://github.com/Windower/Lua/wiki/Events#event-list). Regression checks replay quiet 61-second traffic intervals with missed reports, three consecutive failures, recovery/reset, exact time boundaries and process replacement, alongside the addon filtering and publication-cadence checks.

The final 1.0.27 folder and standalone builds passed package/native Windows validation and 365 core checks. The protected manager was updated normally, and a one-time fixed addon reload command was sent through the existing process-bound input guards to all four verified character windows. Each original PID/start time survived, the new ten-line reports advanced at 30-second intervals, and no new OCR operation ran during the initial live observation. Hauplibond's unblocked-packet counter advanced roughly once per minute while its blocked counter stayed zero: the older packet timestamp reflected sparse chunk observations in that trial, rather than delayed heartbeat publication or filtering observed by this addon. This is not a measurement of transport latency or frame-time impact.

### Validation across updates (1.0.29)

Complete-login proofs now include a fingerprint of the login engine, worker, focus/input guards, profile resolution, credentials, account model, login caches, session IPC and OCR script. The fingerprint normalizes source line endings and ordering. App version, assembly module ID, release notes, artwork and packaging do not participate. Rebuilding the same login implementation preserves validation; changing a fingerprinted source or an account mapping requires validation. This is conservative: even a nonfunctional edit to a fingerprinted source changes its fingerprint.

Only the three explicitly reviewed deployed 1.0.26/1.0.28 module IDs used by the existing accounts are accepted as legacy proofs for this precise baseline. The bridge checks the same account mapping and proof date, rejects unknown build IDs and explicit incompatible flow fingerprints, and automatically stops accepting legacy proofs if the baseline sources change. It does not invent a full-login result or rewrite existing proofs. The module ID remains recorded for diagnostics. Confirmed-disconnect recovery retains its separate matching-prior-proof path.

### Updater preparation (1.0.30)

The previous engine had no updater recognition, a six-minute engine/eight-minute worker limit, and an immediate 30-second game-window wait after Play confirmation. The prepared path recognizes an explicit Version Update heading and specific availability/confirmation/progress/completion wording, checks unique control geometry twice, and waits through the update before resuming normal login. A separate per-user file lock serializes updater access. Other POL processes for the installation must have stable PlayOnline Viewer startup windows; game, character or ambiguous windows block patch-related input. No account is closed to make room for an update.

Update progress waits five seconds between captures, permits up to two hours overall, and stops after 15 minutes without changed phase/file/count/percentage evidence. The full-login request envelope includes this budget; short inspection/calibration and in-place disconnect requests retain their existing limits. Unknown text never authorizes a button. Numeric errors, repair routes and restart requests preserve the process rather than forcing cleanup or guessing. Square Enix's [July 2026 starter guide, Step 6](https://forum.square-enix.com/ffxi/threads/64413-FINAL-FANTASY-XI-Starter-Guide) describes Play → Update → OK; its [version-update instructions](https://support.na.square-enix.com/document/manual/20/FFXI_manual_vc09_AE5.pdf) also establish the Version Update heading; the current client layouts still need a real patch trial.

## Windower Hook.dll failure on closing pre-login POL

Analysis of the saved `CrashDumps/POL/pol.exe.18220.dmp` identified a failure during normal process teardown. The process had run for 105 seconds. The user recalled closing the test POL window around that time to restart automated login, consistent with the dump. This is separate from the earlier DirectDraw startup faults.

Verified dump evidence:

- The exception is `0xc0000409` with parameter `7`, decoded by the debugger as `FAST_FAIL_FATAL_APP_EXIT`. The instruction at `Hook+0xc739a` is `int 0x29` with `ECX=7`.
- The main-thread stack includes `kernel32!ExitProcess(0)`, `ntdll!RtlExitUserProcess`, `ntdll!LdrShutdownProcess`, Hook's DLL detach code, and its C-runtime exit callbacks. This is not the account manager's forced `TerminateProcess` cleanup path.
- The exit callback saved in the caller's local at `0x001afaac` points to `Hook+0x122bb0`. That callback tests the value at `Hook+0x1cddcc` and, when nonzero, branches to the termination routine at `Hook+0xb7e29`, which calls the abort routine at `Hook+0xc7371`.
- The associated two-word thread object at `Hook+0x1cddc8` still contains handle `0x320` and thread ID `0x3bd4`. The worker-loop flag at `Hook+0x1a13c4` remains `1`.
- Initialization code at `Hook+0x2ee10` constructs this thread and registers the failing exit callback. A separate cleanup path near `Hook+0x6eb2a` clears its worker flag, signals its event, and calls the join routine at `Hook+0x35b00`, which clears the thread handle/ID on success. That state had not been reached when the exit callback ran.
- The dump contains dgVoodoo 2.87.5 DirectDraw and no loaded LuaCore or FFXI main module. There is no addon execution frame on the failing stack.

The thread constructor, join implementation and destructor guard match the Microsoft C++ `std::thread` lifecycle. **The immediate cause is destruction of a still-joinable Windower worker-thread object during POL exit, invoking termination and abort.** The most likely underlying defect is a missing or incorrectly ordered worker cleanup path when POL closes before FFXI initialization completes. The worker's private source-level name and the exact reason that normal cleanup was skipped remain unverified because matching private Hook symbols/source were not available. A joinable thread object does not prove its OS thread was still executing at process teardown.

Microsoft documents that [fast-fail uses its first exception parameter to identify the reason](https://learn.microsoft.com/en-us/cpp/intrinsics/fastfail), and its [C++ thread destructor terminates if the object remains joinable](https://github.com/microsoft/STL/blob/main/stl/inc/thread). The generic Windows wording “stack buffer overrun” is not sufficient to diagnose memory corruption for this subcode.

The initial dump-only investigation did not patch Hook, remove plugins or restart live sessions. The actual correction belongs in Windower's worker lifetime/cleanup code; any proposed fix should be validated with a disposable pre-login launch/normal-close cycle and a separate full-login/shutdown cycle. Do not blindly add waits inside DLL detach, where loader-lock restrictions apply. The saved dump and bounded debugger transcripts are retained locally for a maintainer report if requested.

### Controlled reproduction with Minibubble

At the user's request, Minibubble was gracefully shut down through the manager's authenticated session control. Nanakia, Luckystrikes and Hauplibond were recorded as protected sessions by PID plus creation time. Mini was then launched through the manager without invoking login or reading credentials.

At 08:38:10 EDT on October 21, the test helper sent one normal window-close request (`Process.CloseMainWindow`, rather than forced termination) to Mini's responsive pre-login POL window, PID 4240. The process exited with `0xc0000409`. Windows saved `CrashDumps/POL/pol.exe.4240.dmp`.

The new dump reproduced `Hook+0xc739a`, subcode `7`, the `ExitProcess(0)`/DLL-detach stack, and the joinable thread object. Its handle and thread ID were `0x314` and `0x30dc`; the worker flag remained `1`. This confirms the failure can be triggered by a normal close before login. Each protected session retained its original PID/creation time and remained responsive before and after the close trial.

The installed stable Hook matches the official stable-channel binary byte-for-byte (SHA-256 `68d059e8a9e332b274464d6b744a0732bc4a09a49c67d9c07c301c06122ccaa7`). Windower's official development channel supplies a distinct 4.7.9.6 candidate (SHA-256 `c32826605356777a8fb9507c1b238b5ede4da6cb3ef6f491424891db864a8cb5`). That candidate was tested in its own local directory with copied profile settings and no addon autoload. Native Windows module enumeration verified the actual loaded Hook path/version/hash before requesting a normal close; the installed stable Hook remained unchanged.

| Trial | Process | Result |
| --- | --- | --- |
| Stable 4.7.9.3, normal close before login | 4240 | `0xc0000409`, subcode 7, `Hook+0xc739a`; same shutdown failure |
| Isolated development 4.7.9.6, normal close before login, no addons | 2528 | `0xc0000409`, subcode 7, `Hook+0xc74ca`; same shutdown failure |
| Stable 4.7.9.3, existing manager Force close before login | 12328 | Manager verified process exit; no matching Application Error event was recorded for this PID |

The development candidate therefore does **not** fix this defect. Its dump again contains the `ExitProcess(0)`/DLL detach/C-runtime exit callback sequence. No development build was installed into the normal Windower directory.

The manager's existing Force close is a tested operational workaround for a stuck or unwanted **pre-login** POL process. It bypasses Windower's failing teardown and lets Windows reclaim the process resources. This does not repair Hook's worker cleanup; do not describe a forced exit as graceful shutdown or apply it indiscriminately to online games. No binary patch was made and no abort guard was suppressed. A source-level fix or maintainer-provided fixed Hook is still required for a clean normal pre-login exit.

At 08:53 EDT, Minibubble had completed a full login through the normal stable account-manager path, with current-build full-flow validation and a fresh matching Asura heartbeat. The other three accounts still had their original process identities and fresh matching heartbeats; all four windows responded. The final Windows report contained only the two additional controlled normal-close failures, with no extra event from the Force close trial or Mini's restoration. The [reproduction report](HOOK-CLEANUP-REPRO.md), including both builds, stack offsets and the workaround, was submitted as [Windower/Issues #1116](https://github.com/Windower/Issues/issues/1116). Full memory dumps were not uploaded.
